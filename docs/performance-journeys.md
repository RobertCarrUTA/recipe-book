# Supplemental journey timing method

`node scripts/measure-journeys.mjs` supplements the startup/search/detail/large-grocery measurements. Run it from a checkout containing its verified production `dist/`, after `npm ci` and `npm run build`. It serves that output on an ephemeral loopback port with the production server and configured base; it does not build, change the application, or publish anything. `--validate-only` inspects fixtures, build metadata and artifact hashes without launching a browser. `JOURNEY_PERFORMANCE_OUTPUT` overrides the default ignored `test-results/performance-journeys/` directory. Dependencies and build files resolve from the current working directory, allowing the script to run by absolute path from another review checkout.

Run without competing browser/build/performance jobs. Each of the three repetitions at 1440×900 and 390×844 starts a fresh isolated browser context. Service workers stay enabled; the runner waits for activation, control and network idle before timing interactions. It does not simulate a registration failure to suppress caching. Reload measurements use that installed, warm offline shell while recipes follow the application's actual network policy.

The fixture uses the real authored catalog and synthetic personal data: seven days with five recipe assignments per day (three meals plus prepared components/snacks), deliberate repetition across days, eight selected recipes, two favorites, one doubled quantity, and two manual shopping items. It is a busy but bounded weekly plan, not thousands of implausible daily slots. No source recipe or real personal backup is modified. Exact plan/collection/recipe IDs and fixture SHA-256 are recorded.

Measured actions are collection filtering, navigation into the populated 35-assignment plan, cooking entry from its first meal, Dark→Light appearance change, and reopening persisted state. Filtering asserts the expected rendered recipe IDs and total result count; planning compares every day's titles in order; cooking checks the authored first instruction and step-one progress; theme checks the resolved palette, native color scheme and changed computed body surface. An untimed real plan edit adds a 36th assignment before reload. Reload must render that complete plan and Light theme and preserve the exact saved snapshot bytes, including selected recipes and manual shopping data.

Action timing starts immediately before browser click/change dispatch and ends two animation frames after the asserted resulting DOM. A new-document animation-frame observer records reload readiness relative to navigation start, after the expected state has remained rendered for two further frames. These are laboratory event-to-render observations, **not field INP**. The mobile configuration emulates layout on the same desktop CPU; there is no CPU/network throttling. Playwright setup/navigation outside these windows is not an action latency measurement.

Budgets are declared before the first browser run: per-layout action medians ≤200 ms and individual samples ≤400 ms. They match the existing project's 200 ms interaction goal with explicit scheduling headroom, while reporting each action separately. Warm persisted-plan reload has a median ≤1,500 ms and maximum ≤2,500 ms: it must reconstruct the full weekly view promptly, but includes document startup rather than a single interaction. This is a DOM-readiness budget, not an LCP measurement or an assertion that all networks/devices meet it. Existing startup/LCP/CLS budgets remain independent and unchanged.

The runner records all six samples, current Git HEAD/dirty status, built source/release metadata, browser/Node versions, every build-file hash, browser warnings/errors, failing requests and HTTP errors. It rechecks artifact hashes at the end. Missing samples, assertion failures, build changes or exceeded budgets cause a nonzero exit and retain the report. Keep failed reports; investigate before repeating or changing thresholds. Three samples provide a regression signal, not reliable population tail estimates. The generated report and an actual browser run are required before claiming this supplemental gate passed.
